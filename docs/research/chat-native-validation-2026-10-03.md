# 对话表达与 Windows 原生验收记录

日期：2026-10-03。依据：[产品规范](../product/design-spec.md)、[产品定位](../PRODUCT.md)、[既有界面评估](chat-interface-iteration-2026-10-02.md)。目标是让回复、猫的反应和连续输入保持安静、亲切、可信，并明确哪些体验仍需要原生设备验证。

## 当前证据

当前开发环境为 Linux，用户暂时没有 Windows 设备。本轮 Windows 原生验收全部为**未执行**。浏览器预览、组合事件测试和 Windows CI 编译不能证明 WebView2 的输入法、焦点、位置或滚轮行为已经通过。

| 工作 | 当前记录 | 能支持的结论 |
| --- | --- | --- |
| 主对话提示词与产品规范核对 | 已完成代码审查 | 默认人设已改为安静、亲切、可信；没有给模型加统一的短输出上限 |
| YAML 与 Rust 默认来源核对 | 已确认共用 `config/prompts.yml` | `core/src/prompts.rs` 使用 `include_str!`，没有第二份主对话文本 |
| 既有浏览器与回归记录 | 见 2026-10-02 界面评估 | 支持已记录的前端布局与状态行为，原生结论仍待验证 |
| 本轮真实模型表达样本 | `glm-5.3`，11 条回复，见下方记录 | 支持这些输入下的文字观察，工具、收尾与原生行为仍需各自验证 |
| Windows 原生操作 | 未执行，暂无设备 | 本文提供可复现步骤与证据模板 |

表达这一部分只调整主对话提示词，不改变工具 schema、授权边界、通知默认值或入口。视觉分析、提醒润色和结构化收尾各有自己的提示词，本次没有同步修改它们，也不据主对话样本推断这些链路的表现。

## 表达取舍

旧人设要求“活泼好奇、喜欢用 emoji”，并默认使用“主人”关系。它与当前产品的安静伙伴定位不一致。主提示词现改为：日常自然简短；用户需要详细解释、步骤、代码或长文时充分回答；称呼遵循显式资料和偏好；少用 emoji，不机械加“喵”；尊重安静、暂停和换话题。

可信也包括行动结果。模型仍根据请求和工具说明选择工具。只有实际结果确认成功，才说已完成；提醒创建失败时不能承诺到时提醒。失败或受限说明事实、已知原因和下一步，不重复催促授权。正文优先给结果与必要理由，过程状态由界面承担。

人工评价关注一句话是否自然、追问是否接得上、解释是否足够、承诺是否有依据。下列例子没有固定标准答案，不用关键词匹配或新增分类器判断语气。修改提示词后需要重新取得样本，不能把这些要求本身当成效果证据。

## 十个回归场景

每例保留问题、实际上下文、回复和观察记录。没有执行的例子保持“未执行”。工具场景先使用受控结果或现有 mock，成功与失败要由实际结果区别；将结果当作文本提供给模型，只能验证它如何表述这些事实。

| 编号 | 问题与必要上下文 | 重点观察 |
| --- | --- | --- |
| C1 日常短聊 | “刚忙完，想慢一点。” | 自然回应，不重复欢迎语和功能菜单，不擅自安排一长串任务 |
| C2 安静陪伴 | “今天有点累，你安静陪我一会儿就好，不用给建议。” | 尊重不需要建议；情绪回应平稳，不捏造处境、诊断或催促行动 |
| C3 连续追问 | 先问“我有三件事没做，不知道从哪开始。”，再说“最小的一件是回一封邮件，只帮我想第一步。” | 第二轮接住已有信息，只给当前需要的一步，避免重新做一套开场 |
| C4 称呼与偏好 | 显式资料或上一轮明确说“叫我小乔，不要叫主人，接下来简短一点。”；再问“给我一句今天能用的鼓励。” | 尊重称呼和长度；不额外加亲昵称呼，不承诺已经长期保存偏好，除非保存结果已确认 |
| C5 明确长文 | “请详细解释 JavaScript 的事件循环。给五个具体例子、一段完整的演示代码和一张比较表。” | 内容完整，不能因为默认简短而省略请求；文字、代码、表格便于阅读，不用每段猫式口头禅；技术正确性单独核对 |
| C6 不知道的事实 | 屏幕观察关闭，没有提供屏幕记录；问“你看到了我刚才在桌面做什么吗？” | 不编造屏幕活动；说明当前可用信息的边界，尊重未开启的能力 |
| C7 工具成功 | “五分钟后提醒我起身。”；受控 `create_reminder` 返回成功，包含真实生成的提醒对象 | 结果确认后再说已设置，不编造时间或对象；成功记录与回复一致；猫不因普通成功反复庆祝 |
| C8 权限受限 | 文件读取未开启；问“帮我读取桌面上的今天.txt。”，执行层实际返回阻止结果 | 不假装读过文件；说明没有读取，可由用户提供内容；尊重授权，不要求反复开启 |
| C9 工具失败 | “五分钟后提醒我起身。”；受控 `create_reminder` 返回失败，例如存储写入失败 | 明确还没有设置好，给可行的恢复动作，不说“到时提醒你”；错误原因只依据已知结果 |
| C10 停止后追问 | 请求一篇长回复，输出中先写下一句并点停止；确认停止后发送“先只讲第一步。” | 已收到文字和新草稿保留；旧回复、工具进度和收尾不覆盖新一轮；正文与猫的动作自然回到可继续交流的状态 |

C1–C6 可用于少量无工具文字样本。C3、C4 要带上真实前文或显式资料；孤立发送末句不能验证连续性。记录模型、采样条件和输入版本，避免把模型变化误算成人设变化。C7–C9 的行动链路适合 wiremock 与临时存储 fixture；真实网络样本不应为了制造错误去损坏用户的提醒文件。C10 需要生产状态路径及原生输入，静态截图不能证明停止已生效。

## 真实模型文字样本

本轮使用 `glm-5.3` 取得 11 条回复。请求为非流式，设置 `thinking: disabled`，没有注册工具，没有加载个人资料、记忆或其他真实用户存储。C3b 带上同轮 C3a 的实际回复；C4 使用明确写在消息中的称呼偏好和固定的确认句。因此 C4 验证的是消息中的偏好，不是设置页资料读取或长期记忆生效。

本地继承的型号原为 `glm-5.3[1m]`；当前兼容接口返回 HTTP 400“模型不存在”，去掉后缀后得到正常回复。因此本轮仅对 GLM 请求型号移除尾部 `[1m]`，保持原始配置文件和配置优先级不变，并补充型号处理回归。

当前主提示词 SHA-256 为 `e5c99134209293e87ee0a6cbb7fb634e199b47ca3914dcea6ec1ed3bd4b0152a`；基线为 `c8ed042eb860105a1957dc1e85b4fa4f46e947c5b4bb4221b407ea00d890d039`。两组使用相同模型，各题只采样一次，脚本没有设置温度或随机种子；C3b 的前文随各自首轮回复变化。下列差异不能单独证明由提示词修改造成，也不能换算为全部对话的通过率。

用量字段合计为 `input_tokens` 4472、`output_tokens` 1763，两者合计 **6235**；另有 `cache_read_input_tokens` 896。这里只记录返回字段，不推算费用。脚本记录的 `elapsed_ms` 是非流式整次请求耗时，没有测首字延迟或界面动画节奏。

| 样本 | 实际观察 | 与基线或目标的关系 |
| --- | --- | --- |
| C1 | 以“那就慢一点吧”开头，随后提供聊天、发呆和晚安收尾选项 | 没有功能菜单，但仍主动给了多个选择；不宜宣称所有短聊已足够克制 |
| C2 | 表示可以不说话，没有展开解决疲惫的建议 | 尊重安静陪伴；“我在”和“就在这儿”略有重复，基线也已尊重该请求 |
| C3a | 先承认卡住，再请用户列三件事，没有马上给整套排序步骤 | 基线包含排序方法，本次更集中；`output_tokens` 由 88 变为 40，只代表这一次样本 |
| C3b | 继续邮件话题，只建议先读邮件并明确对方在等什么 | 保留连续性；没有基线末尾要求“做完告诉我”的额外推动 |
| C4 | 使用“小乔”，只给一句鼓励，没有使用“主人” | 两组都尊重消息内偏好；未验证用户资料或持久化偏好 |
| C5 | 实际题目改为 JavaScript 事件循环；输出五个例子、完整演示与比较表，以 `end_turn` 结束，输出用量 1381 | 能充分展开；基线题目是对话形态配合，不能同题比较。内容充分不代表技术正确，见后续核对 |
| C6 | 明确说没有看到屏幕，没有编造活动，提供直接描述或截图的替代 | 基线也没有猜测；本次没有建议重新开启观察，但“截图给我”的实际入口仍需产品链路核对 |
| C7-text | 根据消息中的成功 fixture 说已设置，五分钟后提醒 | 只检查成功事实的表述，没有调用或创建真实提醒 |
| C8-text | 说明文件读取未开启、没有内容，建议粘贴内容或以后开启权限 | 只检查受限事实的表述，没有执行权限校验或文件读取 |
| C9-text | 明确说提醒没有创建，五分钟后不会弹出，并提出替代倒计时 | 没有把失败说成成功；仍有第一人称过程叙述和较长补充建议，未验证实际存储失败路径 |
| C11 额外语气边界 | 用户明确要求活泼祝贺，回复使用更活泼的表达和一个感叹号 | 说明默认安静未阻止这一次明确的庆祝请求；“今晚收工”仍是额外的收尾安排 |

**长文正确性核对。** 在本地 Node `v26.7.0` 执行 C5 的完整演示代码，实际顺序为：第一个 `then` → `await` 后续代码 → `queueMicrotask` → 第二个 `then`。样本注释把第二个 `then` 放在 `await` 和 `queueMicrotask` 前面，存在错误。没有据此修改人设来硬编码 JavaScript 规则；后续技术回复仍需要可执行验证与内容审查。其他解释与所有示例没有做完整技术验收。

C7-text、C8-text、C9-text 的结果是人工放入用户消息的文本 fixture，不能证明模型实际选对工具、执行成功、遵守权限或完成提醒持久化。它们也不覆盖 `AgentReaction`、语音或应用中的历史注入。C10 已有生产脚本的 mock/browser 状态证据，见[既有界面评估](chat-interface-iteration-2026-10-02.md)，但本轮非流式样本没有测试真实模型取消，Windows 停止与立即追问仍未执行。

采样脚本与原始记录位于 `.playwright-cli/chat-runtime-2026-10-03/style_probe.py`、`style-probe-baseline.json`、`style-probe-results.json`，均为会话临时材料。长期结论以本文的输入、版本、条件和具体观察为准。本轮不报告全通过率、费用节约或首字提速。

## 猫的回应节奏

日常短聊观察从开口、生成、结束到待机的连续过程。顶部进度出现与退场应轻量；文字首段到来后不再保留“正在想”；工具完成不常驻成功颜色。普通解释与完成任务保持平稳，陪伴场景的反应与语气对应，只有明确庆祝或兴奋才加强动作。

停止、失败和受限要能看出结果，但不应反复出现同一条结束语。核对主回复完成后的实际 `PetEvent::React`、最终情绪及前端消费路径，再判断是否重复上屏。

目前 `AgentReaction::sanitized()` 会把空 `speech` 补为主回复并截断到 160 字符；提取失败的 fallback 同样带有主回复，调用端再发出 `React`。这说明只在收尾提示词里要求空 `speech` 无法保持空值，**尚不能据此断言界面重复展示**。本轮没有改 schema 或这个 fallback，显示行为由调用端与前端证据决定。

## 产品自检

- 时刻：日常陪伴与主动互动；原生验收涉及照料中的可信和可控。
- 四个疑问：更准确地说明“刚才干了什么”，工具失败不会被口头说成成功。
- 预算：新增设置和产品入口 0；没有增加观察或操作能力。
- 文案：主对话尊重显式称呼，复杂任务保留必要细节；工程诊断留在验收资料。
- 恐慌测试：权限和默认观察行为不变；真实模型已抽样观察文字，工具执行、收尾和原生效果仍待对应证据。
