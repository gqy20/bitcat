# API 连接界面调研与 BitCat 改造建议

调研日期：2026-09-18。阅读官方文档，并实际查看 Jan 与 Open WebUI 文档中的界面截图；不是各客户端的实机操作测试。官网文档截图可能落后于软件版本，因此只提炼交互结构，不照搬版本相关字段。

## 参考产品

| 产品 | 官方设计中可确认的做法 | 对 BitCat 的启发 |
| --- | --- | --- |
| Cherry Studio | 服务商配置页组织密钥、模型列表和检测操作，特殊选项进入高级设置 | 基础配置形成一个可验证的流程，模型名称与实际 ID 分层展示 |

## 当前界面的问题

1. 左侧标签旁堆有效值，右侧又放覆盖值输入框，同一字段存在两条阅读路径。用户需要理解“覆盖配置”才能编辑。
2. 密钥、地址、模型、回复长度平铺，视觉权重相同；连接必需项与调优参数没有区分。
3. 连接配置位于图表和活动记录下方，初次设置需要先经过无数据或无关信息。
4. `has_effective_key` 只证明配置存在；页面的绿点及“一切正常”不能证明服务可达、认证通过或模型可用。
5. API Key 输入框提示“已保存则留空”，但 `saveAll()` 将空值发送为 null，`cmd_settings_save_ai` 用它替换原有覆盖值。当前输入框通常会回填本地覆盖密钥，因此不是每次保存都会清除；但用户按提示清空后会清除本地密钥覆盖或回退到其他配置来源。
6. 只用统一字号、移除分隔线无法解决上述阅读与操作问题。

代码依据：`app/frontend/js/settings.js` 的 `renderAi`、`renderOverviewNotices`、`saveAll`；`app/src/settings.rs` 的 `AiView`、`cmd_settings_load`、`cmd_settings_save_ai`；`core/src/ai_config.rs` 的 `load`。

## 推荐结构：连接摘要 + 行内编辑

保留 4+1 导航。把“AI 服务”摘要移到用量页上方，未配置时直接展开编辑；已配置时通常只显示一行服务与当前模型，右侧为状态及操作。

默认摘要示意（仅用于表达设计，不代表真实检测结果）：

```text
AI 服务                                      配置已保存 · 尚未检测
[服务图标]  Anthropic · 当前模型名称             修改连接   检测连接
```

点击“修改连接”后在同一区域展开，避免另开弹窗：

```text
连接方式          [ 官方服务 / 自定义兼容服务 ]

API Key                                      获取密钥 ↗
[ 已保存的密钥保持不变；输入新密钥时替换                显示 ]

模型
[ 当前模型 ID，可编辑                                      ]

服务地址（自定义时显示）
[ https://你的服务地址                                    ]

▸ 高级设置

检测结果或错误说明                       取消修改   保存连接
```

视觉规则：

- 摘要是一个横向信息单元，使用小服务标识，不新增大面积 Logo 网格。
- 展开态的标签在输入框上方，不再把长有效值塞在标签与输入框之间。
- 表单宽度限制在约 520–600px，单列对齐；字段间距 18–22px，依靠留白分组，保留输入框边界，不加行分隔线和嵌套卡片。
- 模型选择暂时使用可编辑 ID；后续有真实模型发现接口再升级为可搜索选择器。不能做一个没有数据来源的假下拉框。
- 回复长度上限进入高级设置；内置官方地址不要求用户重复填写。
- 密钥不在输入框之外重复显示。编辑、取消、清除必须有明确语义；从外部配置继承时只显示来源与状态，不假装能显示该密钥。
- 沿用统一排版角色，绿色用于通过检测，灰色用于待检测；未检测不能只放一个容易被误解为“已连接”的绿点。

## 状态与操作

状态至少区分：未配置、已保存但未检测、检测中、检测通过、检测失败、修改后待重测。修改地址、密钥或模型后必须使旧检测结果失效。

“保存连接”只保存当前连接草稿，不能顺便保存其他分区未提交的改动；原全局保存仍应兼容连接草稿，退出/取消遵循既有 dirty 提示。新增局部操作时收纳高级字段，避免扩大常驻控件预算。

错误要能指导下一步，例如：

- 服务没有接受这个密钥，请检查密钥是否复制完整。
- 当前模型不可用，请检查模型名称或选择其他模型。
- 暂时连不上服务，请检查地址和网络后重试。

原始诊断细节折叠。仅能列出模型，不等于实际对话可用；检测应标明它验证了什么。若使用一次最小对话验证，按钮旁说明可能产生少量用量，由用户点击触发，不能在打开设置页时自动请求。

## 实现边界与顺序

当前 `PetAgent` 使用 `anthropic::Client`。首轮仅设计 Anthropic 官方服务与兼容 Anthropic Messages 的自定义地址；不能只加一个 OpenAI/Gemini 服务商按钮就宣称协议已支持。

1. 优先：重排摘要与表单，区分当前状态和编辑草稿，修正留空/替换/取消语义，收纳高级设置。
2. 接着：增加 Rust 侧连接检测，验证草稿配置且不先覆盖现有连接；返回结构化结果、处理超时并避免在日志中记录密钥。
3. 后续：有真实需要再做模型列表发现、多服务商或多密钥；不照搬通用聊天客户端的完整管理后台。

## 产品自检（设计阶段）

- 时刻：照料，让用户知道服务是否可用以及如何修复。
- 控件预算：日常显示摘要与少量操作；高级字段默认折叠，实施时清点全局预算。
- 默认值：不改模型、不自动开启能力，不主动测试用户服务。
- 数据：调研与本地源码核对；没有使用用户真实密钥或发起模型请求。
- 本次产物：调研及设计建议，尚未变更 API 配置实现。
