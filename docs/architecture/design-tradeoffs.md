# 设计取舍记录

> 这个文件集中记录项目明确不采用的方案，以及背后的判断标准。目的不是否定某类技术本身，而是避免同一个复杂方案反复回到路线图里。

## 原则

1. 大模型擅长的简单理解，不在本地重复做低质量规则系统。
2. 能用可读文本、文件系统和 grep 解决的问题，不优先引入数据库、向量索引或额外服务。
3. 优先保留数据的可检查性：人能打开、能搜索、能 diff，模型也能直接读懂。
4. 复杂基础设施必须证明收益大于维护成本，否则先不做。

## 不采用：关键词意图识别

### 被拒绝的方案

在 Rust 或前端里用关键词、正则或小分类器判断“用户是不是要跳舞 / 闲聊 / 执行工具”，再决定走哪条逻辑。

### 为什么不做

- “跳个舞”“来点开心的”“整活一下”这类表达本来就是大模型擅长理解的简单语义。
- 关键词匹配会制造大量边界问题，还会把产品体验拉回命令式交互。
- 额外发起一次分类调用也不优雅：增加延迟和 token，收益却很小。

### 当前取舍

让模型在普通对话里看到工具，并自行决定是否调用。Rust 只负责强类型边界、校验、权限和执行结果。

## 不采用：Embedding / Vector RAG 记忆

### 被拒绝的方案

为长期记忆引入 embedding provider、向量索引、相似度检索、重建/过期/缓存策略，把历史对话做成语义向量库。

### 为什么不做

- 本项目当前记忆和日志规模很小，grep / ripgrep 级别的文本搜索速度远快于实际需求。
- 向量检索会引入额外依赖、额外 API 或本地模型、索引持久化、冷启动、重建、漂移等维护成本。
- 向量结果不可读、不可 diff，不利于调试“为什么召回了这条记忆”。
- 大模型已经足够聪明：给它干净的文本候选、时间、来源和片段，它能很好地判断哪些有用。

### 当前取舍：grep-first 记忆

长期记忆应优先演进为“可 grep 的文本记忆系统”：

- 一行一条的 JSONL record / Markdown 片段，字段稳定；
- 每条记录保留时间、来源、标签、摘要、原始短文本；
- 需要召回时先用关键词、时间范围、最近活动、文件名等可解释条件筛出候选；
- 把候选片段交给大模型做最终判断和压缩；
- 用 `rg` / grep 风格检索，而不是向量数据库。

### 当前实现补充（2026-05-15）

长期记忆已经从关键词式 `should_store()` 迁移为 `AgentReaction.memory_candidates` 驱动。每条候选由 rig `Extractor<AgentReaction>` 生成，Rust 负责长度、标签和重要度等边界校验。

`LongTermMemory` 当前提供：

- `record_candidate()`：写入 summary/tags/importance/source。
- `retrieve_with()`：按 text/tag/source/min_importance 进行可解释过滤。
- `review_entries()` / `review_markdown()`：输出可人工审查、可 grep 的结构化视图。

这仍然遵守 grep-first 原则：候选生成可由模型判断，但持久化形态必须能被人打开、搜索、diff 和删除。

### 推荐形态

```text
~/.ai-pad/memory/
├── chat_summary.json          # 当前滚动摘要，继续保留
├── long_term.jsonl            # 当前有效长期记忆 record，可 grep，deleted 软删除
├── daily/2026-05-13.md        # 可选：按天沉淀的人类可读摘要
└── index/
    └── tags.json              # 可选：轻量标签索引，不是向量索引
```

候选查询可以是：

```powershell
rg -n "Tauri|截图|token|日志" ~/.ai-pad/memory
```

程序侧可以封装为：

```text
MemorySearchQuery {
  text: String,
  since: Option<DateTime>,
  limit: usize,
  sources: Vec<MemorySource>,
}
```

但底层仍是可解释的文本检索与排序，不做 embedding。

## 不采用：为了省 token 过早裁剪工具

### 被拒绝的方案

按本地规则判断“这个消息只需要少数工具”，从而动态裁剪工具集。

### 为什么不做

- 工具是否需要调用，交给模型判断更自然。
- 裁剪错一次就会让模型失去能力，体验损失比节省几百 token 更明显。
- 现在已经有 token 统计，应该先看真实消耗，再优化工具描述和 schema。

### 当前取舍

默认继续给模型完整能力。优化顺序是：

1. 看 `token_usage.jsonl` 和设置页统计；
2. 压缩工具描述；
3. 合并重复工具；
4. 必要时用显式模式启用低频能力；
5. dynamic tools 只作为 feature flag 实验，不作为默认架构。
