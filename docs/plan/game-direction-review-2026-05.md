## 一、为什么补这份文档

过去一段时间，仓库里已经分别从小游戏系统、成长系统、Hub World、RPG 和 3D 架构几个角度讨论过“BitCat 以后还能玩什么”。这些想法分散在多份计划和 GDD 中，容易出现两个问题：

1. 新想法来了以后，不清楚它和已有规划是重复、补充，还是方向冲突。
2. 近期能做的小步快跑目标，和长期的大游戏愿景容易混在一起。

这份文档的目的不是重新发明路线，而是把现有方向收拢成一张可执行的地图：哪些已经实现，哪些只是远景，哪些最适合接在当前 5 个内置小游戏后面继续做。

## 二、当前已落地的游戏薄片

当前桌面版已经具备稳定的小游戏骨架：

- 透明置顶 `game` 窗口
- `GameDef` / `MinigameType` / Rust 校验
- `start_game(kind)` AI 工具
- 键盘 / 手柄独占输入
- 宠物 `GamePlay` / `GameWin` / `GameLose` 联动

目前已实现 5 个内置玩法：

1. Snake
2. Memory
3. Catch
4. Battle（当前已演进为飞机守护战）
5. Gomoku

它们已经证明了两件事：

- BitCat 适合“短局、随时打开、反馈明确”的轻玩法。
- `game window -> GameDef -> front-end engine` 这条链路足够稳定，继续加内置玩法的成本是可控的。

## 三、仓库里已经出现过的后续游戏方向

### 3.1 小游戏系统继续扩展

来源：

- [minigame-system.md](minigame-system.md)
- [../roadmap.md](../roadmap.md)

已明确写过但尚未完成的事项：

- `config/minigames.yml` 预设体系
- `save_game()` / `load_game()` / `list_games()`
- 分数 JSONL 持久化
- `perform_game`：AI 生成完整 `GameDef`
- `play_game`：按保存名称或预设启动

这条线的特点是：

- 与当前代码最连续
- 工程风险最低
- 更偏“游戏系统化”，不是“玩法范式升级”

适合作为底座建设，但它本身不会自动带来“BitCat 味道更强”的新玩法。

### 3.2 Mini-game 作为性格展示舞台

来源：

- [../gdd/core-gameplay.md](../gdd/core-gameplay.md)

GDD 中已经给出一个重要判断：mini-game 不是独立产品，而是 **BitCat 性格的展示舞台**。文档里提过的方向包括：

- 核心玩法：打砖块、节奏游戏
- 休闲玩法：贪吃蛇、反应测试
- 彩蛋玩法：BitCat 自主玩给你看、猜拳

这条线强调的不是玩法品类本身，而是：

- 同一个玩法里，不同性格的 BitCat 表现不同
- 玩法是人格、情绪和陪伴关系的外化

这是当前桌面版最值得保留的原则。

### 3.3 训练场 / Hub World 化

来源：

- [../gdd/core-gameplay.md](../gdd/core-gameplay.md)

文档中已经把“训练场”定义为唯一值得正式叫“模式”的内容。它不是独立游戏，而是营地里的一个工具性入口。已提到的训练内容包括：

- 战斗配合训练
- Boss 复盘
- 舞蹈编排测试
- BitCat 模拟器

这条线说明：未来这些小游戏和互动能力，最终并不想彼此孤立，而是可能被收编进一个更大的营地 / Hub World 结构里。

### 3.4 俯视角 RPG + AI NPC + AI 地图生成

来源：

- [topdown-rpg-ai.md](topdown-rpg-ai.md)
- [../gdd/world-combat-player.md](../gdd/world-combat-player.md)

这条线已经不是小游戏扩展，而是完整游戏方向。文档里已经讨论过：

- 俯视角 RPG 比横版更适合当前工程约束
- NPC 对话复用现有 agent 管线
- AI 生成 tilemap 并做连通性校验
- Hub World / 地牢 /战斗配合 / BitCat 伙伴系统

这条线想象力很强，但体量明显已经超出“给当前桌面版加第六个小游戏”的范围。

### 3.5 3D / voxel 游戏化

来源：

- [3d-architecture.md](3d-architecture.md)

这里的长期目标更大：

- 短期：桌宠 3D 化
- 长期：AI 生成完整 3D 游戏场景

它和小游戏相关，但更多是渲染与内容生产层升级，而不是近期玩法选择问题。

## 四、当前阶段不建议直接做的方向

结合现有实现状态，以下方向虽然文档里已经存在，但不适合作为“小游戏下一步”的直接目标：

### 4.1 直接进入完整 RPG

原因：

- 代码量和资源量级跳变太大
- 需要独立地图、战斗、背包、任务和叙事结构
- 会和当前小游戏薄片争抢实现带宽

### 4.2 先做 3D 再想玩法

原因：

- 3D 不能替代玩法判断
- 在没有确认下一阶段核心体验前，先改渲染栈会放大不确定性

### 4.3 单纯复刻传统休闲小游戏

例如直接复刻矿工、连连看、三消、推箱子。

原因：

- 能做，但容易只得到“又多了一个 mode”
- 没有充分利用 BitCat 已有的语义资产：记忆、提醒、Agent Watch、观察、宠物事件、成长系统

## 五、近期最值得尝试的方向

### 5.1 推荐方向：BitCat 语义化小游戏

目标不是找一个现成品类原样照搬，而是把 BitCat 现有系统里的概念变成玩法目标、风险和反馈。

可用素材包括：

- `treat`：宠物零食、分数目标
- `memory_shard`：长期记忆标签的抽象碎片
- `reminder_note`：提醒系统的投影目标
- `agent_task`：Agent Watch 中等待处理的任务投影

关键原则：

1. 这些元素只做“游戏投影”，不直接修改真实记忆、提醒或任务数据。
2. Rust 只向前端暴露安全摘要，不把隐私正文和真实控制权交给小游戏。
3. 玩法应优先复用当前 `game` 窗口和 `GameDef` 链路，而不是另起一套世界模拟。

### 5.2 当前最值得原型化的具体方案

推荐名称（工作名）：`Invasion` / `桌面小怪入侵`

原型目标：

- 小怪从屏幕边缘或游戏场内入口出现
- 试图“偷走”鱼干、记忆碎片、提醒便签、Agent 任务卡
- 玩家与 BitCat 一起拦截、保护、回收目标
- 胜负仍然走现有小游戏生命周期

它之所以适合作为下一步，是因为：

- 能继续复用内置小游戏架构
- 能直接体现“BitCat 不是普通小游戏合集，而是把桌宠语义游戏化”
- 规模可控，可以先做 1k~1.5k 行的 MVP

## 六、建议的近期路线

### Phase A：先把小游戏系统底座补齐

继续推进：

- 预设体系
- 分数 JSONL
- `GameDef` 持久化
- `perform_game` 的工具边界设计

这是后续所有玩法继续扩展的共同基础。

### Phase B：做一款“语义化小游戏”验证方向

推荐优先做：

- `Invasion` 内置模式

先不做：

- 真实桌面截图生成地形
- 复杂 AI 导演关卡
- 真实 pet 窗口参与物理碰撞
- 跨窗口大型场景模拟

MVP 只验证一件事：

> 把 BitCat 的记忆 / 提醒 / Agent 语义映射为游戏目标后，玩法是否明显比传统小游戏更有项目辨识度。

### Phase C：验证成功后，再决定往哪条大线收束

如果 `Invasion` 这类玩法证明“语义化小游戏”有效，再决定下一步是：

1. 继续扩展更多语义化 mini-game
2. 把这些玩法收编进训练场 / 营地
3. 往俯视角 RPG / Hub World 迁移

## 七、结论

当前仓库里并不缺“未来能做什么”的想法，真正缺的是一条把现有能力和长期愿景接起来的中间路线。

这个中间路线不应该一脚迈进完整 RPG，也不应该退回单纯复刻传统休闲小游戏。更合理的做法是：

- 底层继续把小游戏系统补完整
- 玩法上优先尝试 **BitCat 语义化小游戏**

因此，接在当前 5 个内置游戏后面，最推荐的不是盲目增加第 6 个传统品类，而是做一个能让提醒、记忆、Agent Watch 和宠物反应真正参与进来的原型玩法。
